# AGENTS.md — MARATHON Tactical

Инструкция для coding-агентов (Codex, Antigravity), работающих в этом репозитории над проектом **MARATHON Tactical**.

---

## 1. Источники истины и приоритет документов

1. [`docs/PRODUCT_SPEC.md`](docs/PRODUCT_SPEC.md), [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), [`docs/DESIGN_SYSTEM.md`](docs/DESIGN_SYSTEM.md) — спецификация продукта, слои архитектуры, дизайн-токены и критерии приёмки.
2. [`docs/DECISIONS.md`](docs/DECISIONS.md) — утверждённые архитектурные решения и адаптации (имеют приоритет, если уточняют исходные предположения после проверки реальной среды).
3. [`docs/ENVIRONMENT_REPORT.md`](docs/ENVIRONMENT_REPORT.md) — подтверждённые факты об окружении Windows 11 и неподтверждённые параметры целевой среды CachyOS.
4. [`docs/DEVELOPMENT_STATUS.md`](docs/DEVELOPMENT_STATUS.md) и [`docs/REVIEW_HANDOFF.md`](docs/REVIEW_HANDOFF.md) — актуальный статус этапов (1–10) и фактический отчёт для внешнего ревью.
5. [`docs/AGENT_SKILLS.md`](docs/AGENT_SKILLS.md) и локальные навыки в `.agents/skills/` — рабочие регламенты для конкретных доменов.

При конфликте между спецификацией и фактическим API установленной версии (Hyprland, Quickshell, Qt6) **сначала проверь локальную документацию и установленные версии**, затем минимально адаптируй решение и зафиксируй основание в [`docs/DECISIONS.md`](docs/DECISIONS.md).

## 2. Регламент работы по этапам (Единый непрерывный проект)

1. Работа ведётся последовательно по этапам **1–10** (`Аудит` → `Каркас` → `Библиотека компонентов` → `Tactical HUD` → `Launcher` → `Системные панели` → `Linux Integration` → `Оформление` → `Тестирование` → `Релиз`) в рамках единого контекста без требования открывать отдельный чат на каждый этап.
2. Запрещено создавать пустые каталоги-заглушки «на будущее» или имитировать реализованную функциональность.
3. Перед изменениями проверяй состояние рабочего дерева (`git status` при наличии `git`) и открывай **только** файлы, нужные для текущего этапа/модуля.
4. После завершения каждого крупного компонента/этапа:
   - запускай применимые проверки (`pyside6-qmllint`, `QtQuickTest`, preview-рендеринг/скриншоты, статические проверки границ слоёв);
   - обновляй [`docs/DEVELOPMENT_STATUS.md`](docs/DEVELOPMENT_STATUS.md) (и [`docs/REVIEW_HANDOFF.md`](docs/REVIEW_HANDOFF.md) на рубежах этапов);
   - честно помечай проверки, требующие целевой ОС, как `NOT RUN — requires CachyOS`;
   - переходи к следующему доступному этапу, если нет реальных блокеров или требований явного подтверждения со стороны владельца.
5. Делай локальные атомарные коммиты только если владелец разрешил коммиты и `git` установлен; **никогда** не выполняй `git push`, `merge` или релиз без явного разрешения.

## 3. Неизменяемые технические и безопасные ограничения

1. **Windows Preview -> Linux Live:** сначала пиши и проверяй UI через Windows QtQuick Preview (`preview/`) и моки, затем подключай Linux-адаптеры (`shell/services/`).
2. **Строгое разделение слоёв (`UI / State / Adapters`):**
   - Компоненты в `ui/` **не должны** импортировать `Quickshell` (`Quickshell.*`) или `preview/mocks/` напрямую.
   - Данные и команды подаются через единый контракт (`Workspaces`, `ActiveWindow`, `Audio`, `Network`, `Battery`, `Brightness`, `Notifications`, `Session`, `Launcher`, `Appearance`) с обязательными состояниями `available` / `loading` / `error`.
3. **Централизованный дизайн:** все цвета, отступы (`4/8 px`), радиусы, границы (`1 px`), типографика и длительности анимаций хранятся в `ui/tokens/` согласно [`docs/DESIGN_SYSTEM.md`](docs/DESIGN_SYSTEM.md). Никаких разбросанных hex-литералов в компонентах.
4. **Безопасность существующей ОС и удалённого доступа:**
   - **Никогда** не перезаписывай `~/.config/hypr/`, действующую конфигурацию Quickshell, настройки дисплейного менеджера или `/usr/share/wayland-sessions/` без явного opt-in и задокументированного бэкапа/отката.
   - Не отключай `sshd`, RDP/VNC, VPN или firewall и не завершай автоматически активную GUI-сессию на удалённой машине.
   - Запрещены `rm -rf` по пользовательским конфигам, бездумный `pacman -Rns` и побочное обновление всей системы.
5. **Никаких непроверенных форматов и выдуманных API:**
   - Не предполагай заранее синтаксис Hyprland (`hyprlang` vs `hyprland.lua`) и API Quickshell до проверки целевой системы.
6. **Событийная модель и отсутствие лишнего backend:**
   - Не запускай фоновые Python/Rust/Node IPC-демоны там, где достаточно нативных интеграций Quickshell/Hyprland/D-Bus.
   - Предпочитай события и сигналы вместо частого polling через `Timer`; скрытые виджеты обязаны ставить обновления на паузу / выгружаться (`Loader` / `active`).
7. **Безопасный запуск процессов и `.desktop`:**
   - Внешние команды запускай только с явным массивом аргументов, проверкой exit-code и таймаутом. **Никакого `sh -c` с неэкранированным или пользовательским вводом.**
   - Не реализуй произвольное выполнение shell-команд из поискового поля Launcher без отдельного явно включаемого безопасного режима (белый список команд).
8. **Визуальная верификация и авторские ассеты:**
   - Не объявляй UI «визуально готовым» без просмотра реального скриншота (Windows Preview, затем CachyOS).
   - Используй только авторские геометрические SVG и шрифты/обои с проверенными лицензиями (никаких закрытых ассетов Bungie Marathon).

## 4. Использование навыков (`.agents/skills/`)

Подключай только **1–2 релевантных навыка** под текущий срез (подробности в [`docs/AGENT_SKILLS.md`](docs/AGENT_SKILLS.md)):
- Проверка готовности и честные отчёты: `verification-before-completion`
- Дизайн-токены, состояния, скриншоты: `marathon-design-system` (приоритет всегда у [`docs/DESIGN_SYSTEM.md`](docs/DESIGN_SYSTEM.md))
- Windows Preview и мок-адаптеры: `qtquick-preview`
- Linux Quickshell-панели и адаптеры: `quickshell-expert`
- Профиль, синтаксис и отладка Hyprland: `hyprland-expert`
- Разбор багов и сбоев: `systematic-debugging`
- Подготовка diff к внешнему ревью: `requesting-code-review`

**Не активируй** веб-ориентированные навыки из комплекта `ui-ux-pro-max-cli` (`banner-design`, `brand`, `design`, `design-system`, `slides`, `ui-styling`) для QML/Hyprland-задач.
